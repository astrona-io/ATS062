# How A Result Changes The Rollout, And Experiments

The phase of a run is the signal that the controller reads. This part describes what each final phase does to the Rollout, how to find out why a run ended as it did, and what an `Experiment` adds.

## What each phase does

| Run phase | Effect on the Rollout |
| --- | --- |
| `Successful` | The release continues to the next step or to promotion |
| `Failed` | The release is aborted, and the stable ReplicaSet keeps all traffic |
| `Error` | The release is aborted, because the controller could not decide |
| `Inconclusive` | The release is paused until a person decides |

On an abort, the controller sets `status.abort: true` and moves the weight back to 0. The canary pods are scaled down after `abortScaleDownDelaySeconds`. The phase of the Rollout becomes `Degraded`.

An inconclusive result is a request for a human decision. The phase becomes `Paused`, and a promotion continues the release, while an abort stops it. Use `inconclusiveLimit` to allow a few inconclusive measurements before the pause.

## Finding the reason for a result

Read the run in three steps. First, read `status.phase` and `status.message` of the run. Second, read `status.metricResults`, where each metric has a `phase`, the counters `successful`, `failed`, `inconclusive` and `error`, and the list `measurements` with the value and the time of each. Third, for a `job` provider, read the Job and its pod logs in the namespace of the run, because the log holds the output of the check.

```sh
kubectl -n starfleet get analysisrun -o wide
kubectl -n starfleet get analysisrun <run-name> -o yaml
kubectl -n starfleet get jobs
```

Replace `<run-name>` with a name from the first command. The run name is generated by the controller.

## Retrying an aborted release

An aborted Rollout stays aborted for that revision. The controller does not run the same revision again. To release again, either change the pod template, which creates a new revision, or clear the abort with a retry. The retry starts the revision from step 0 and creates new runs. If the cause was a failing check and you did not fix it, the new run fails in the same way.

## Experiments

An `Experiment` is a third resource. It runs one or more temporary ReplicaSets for a set time and attaches analysis to them. It does not receive production traffic by itself. A canary can use an `experiment` step to start it, and the controller waits for the experiment and its analysis before the next step.

```yaml
steps:
- experiment:
    duration: 5m
    templates:
    - name: baseline
      specRef: stable
    - name: canary
      specRef: canary
    analyses:
    - name: compare
      templateName: probe-gate
```

The field `specRef` copies the pod spec of the stable or the canary ReplicaSet. Running both next to each other lets an analysis compare them under the same conditions. An experiment ends when its `duration` has passed, or earlier if an analysis fails.

## Reading the abort

If you ran the background analysis in the previous part, read what the controller recorded:

```sh
kubectl -n starfleet get rollout mission -o jsonpath='{.status.stableRS} {.status.currentPodHash}{"\n"}'
kubectl -n starfleet get analysisrun -o jsonpath='{range .items[*]}{.metadata.name} {.status.phase}{"\n"}{end}'
```

The two hashes differ, because the new ReplicaSet exists but is not stable. The run list shows a `Failed` run. To release a corrected version, set `status` back to `"200"` in the Rollout and apply it. The controller treats this as a new revision and creates a new run.

## Choosing where to place the analysis

An inline step fits a check that must pass at a certain weight. A background analysis fits a metric that must stay healthy for the whole release. A pre-promotion run fits a smoke test on a preview. A post-promotion run fits a check of real traffic after the switch, with an automatic return to the old version.

## Timing of the decision

The controller reads the run each time it reconciles the Rollout, so a failure is acted on soon after the run reaches its final phase. For a background run, the effect is immediate: the release is aborted in the middle of a pause or a step. For an inline step, the controller does nothing until the run ends, so a long `count` with a long `interval` delays the step by the product of the two. A metric with `count: 5` and `interval: 1m` holds the step for about five minutes.

## Keeping a failed release visible

An aborted release leaves its evidence in the cluster. The failed `AnalysisRun` stays, with all measurements, until the Rollout is deleted or the history limits remove it. The fields `successfulRunHistoryLimit` and `unsuccessfulRunHistoryLimit` under `spec.analysis` control how many finished runs the controller keeps for a Rollout. Keeping unsuccessful runs longer helps a team to find the cause after the release.

## Reading the Rollout conditions

The Rollout also reports analysis in its own status. The conditions list in `status.conditions` has an entry of type `Progressing` with a reason and a message. When an analysis aborts the release, the message names the failed run. Reading the Rollout first and the run second is the fastest way to find the cause, because the Rollout message points to the exact run name.

## Common pitfalls

> [!WARNING]
> An `Error` aborts the release in the same way as a `Failed` run, so an unreachable metric server stops releases. Set `consecutiveErrorLimit` to tolerate short outages. An aborted revision is not retried alone, and fixing the template does not restart it.
